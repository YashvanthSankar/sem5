# Q3 — Semaphore

[Open the exam solution](q3.c)

**Problem: Printer Resource Management Using Semaphores**

A computer laboratory has 3 printers shared by multiple student threads. Write a C program using Pthreads and a counting semaphore to simulate access to these printers.

- Create 6 student threads.
- Each student thread requests a printer using sem_wait().
- Print: "Student X acquired a printer".
- Simulate printing for 2 seconds using sleep(2).
- Print: "Student X released the printer".
- Release the printer using sem_post().

Initialize the semaphore as:

```c
sem_init(&printer_sem, 0, 3);
```

Requirements:

- Create 6 student threads.
- Use a counting semaphore initialized to 3.
- At most 3 students should be using printers simultaneously.
- Use sem_wait() before acquiring a printer.
- Use sem_post() after releasing a printer.
- Use pthread_join() to wait for all threads.
- Destroy the semaphore after all threads finish.

Expected behavior:

```
Available printers = 3

Student 1 acquired printer
Student 2 acquired printer
Student 3 acquired printer

Student 4 waiting...
Student 5 waiting...
Student 6 waiting...

Student 1 released printer
Student 4 acquired printer

Student 2 released printer
Student 5 acquired printer
```

(Note: The exact order may vary due to thread scheduling.)

Concepts tested: Counting semaphore, resource management, blocking, sem_wait(), and sem_post().

## Compile, run and expected output

```text
Compile:  gcc -Wall -Wextra q3.c -o q3 -pthread
Run:      ./q3          (Linux only: macOS does not support unnamed sem_init)

Expected output: the order varies. At most three students have acquired but not yet released
a printer at any instant. With all threads started promptly, the run takes about four seconds.
```

## Answers (viva)

```text
1. sem_init(&printer_sem, 0, 3)
   2nd arg 0     -> shared between the threads of this process (non-zero = between processes,
                    the semaphore must then be in shared memory).
   3rd arg 3     -> starting value = number of printers.

2. sem_wait() (P / down): if value > 0, decrement and continue; if value == 0, the thread
   BLOCKS (sleeps, no busy waiting) until someone posts.
   sem_post() (V / up): increment the value and wake one blocked thread.
   So at most 3 threads are between sem_wait() and sem_post() at any time.

3. Why does the "waiting..." order not match the "acquired" order? printf and sem_wait are two
   separate steps. A thread can print "waiting" and be preempted before it calls sem_wait(),
   so the thread that prints first is not always the one that gets a printer first. The scheduler
   decides, which is why the question says the order may vary.

4. Why does it take ~4 s and not 12 s or 2 s? 6 students / 3 printers = 2 rounds of 2 s.
   That shows the semaphore really limits it to 3 at a time and also lets 3 run in parallel.

5. Why pass &id[i] and not &i? &i is the same address for every thread, and the loop changes i
   before the thread reads it. Two threads could get the same number, or 7.

6. Counting vs binary semaphore vs mutex:
   counting (value N) = N identical resources; binary (value 1) = acts like a lock;
   a mutex is a lock with an owner (only the thread that locked it may unlock it).

7. What if sem_post is forgotten? The value never goes back up. After 3 students the other 3
   block forever, so pthread_join never returns and the program hangs.
```
