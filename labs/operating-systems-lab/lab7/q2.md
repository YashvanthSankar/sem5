# Q2 — Implement process_info(int option) (15 marks)

[Open the exam solution](q2.c)

Lab 7, xv6-public (x86). Copied word for word from the lab sheet. Solution code: `q2.c`.

Implement a new system call process_info(int option) with behavior determined by the integer argument:

| Option | Operation | Return value |
|---|---|---|
| 0 | Get calling process PID | Current PID |
| 1 | Get parent PID | Parent PID |
| 2 | Compute absolute PID difference | \|PID − parent PID\| |
| Other | Invalid operation | −1 |

If the process has no valid parent, options 1 and 2 must return −1.

Tasks
1. Assign an unused syscall number to process_info().
2. Modify syscall.h, user.h, usys.S, syscall.c, and sysproc.c to register and implement it.
3. Retrieve the integer argument with argint().
4. Use the current process structure and its parent pointer to obtain the required PIDs.
5. Implement all operations and invalid-input handling.
6. Create a user-level test program exercising options 0, 1, 2, and an invalid value.
7. Explain transfer of the argument to kernel mode and return of the selected result.

Sample test program
```c
#include "types.h"
#include "user.h"

int main(void)
{
    printf(1, "PID: %d\n", process_info(0));
    printf(1, "Parent PID: %d\n", process_info(1));
    printf(1, "PID Difference: %d\n", process_info(2));
    printf(1, "Invalid: %d\n", process_info(5));
    exit();
}
```

Handout self-check questions also answered below:
5. Why must getppid() check p->parent before dereferencing it?
7. What does argint(0, &option) mean?
8. Why must process_info(2) check for a missing parent?

## Answers

**Task 7: the argument goes in, the result comes out.**
`process_info(2)` in C: 2 is pushed on the **user stack**, then `call` pushes the return address → the usys.S stub sets
EAX = 22 and runs `int $64` → `vector64` → `alltraps` (builds the trapframe) → `trap()` → `syscall()` →
`num = tf->eax = 22` → `syscalls[22]()` = `sys_process_info()` → `argint(0,&option)` = `fetchint(tf->esp + 4)` →
option = 2 → the handler returns the difference → `syscall()` stores it in `tf->eax` → `trapret`, `iret`: the user's
`%eax` = result → the stub runs `ret` → that is the C return value.

```
User program -> process_info(option) -> usys.S (EAX = 22) -> int $64
-> trap() -> syscall() -> sys_process_info() -> argint() reads option
-> switch on option -> return value -> tf->eax -> iret -> user program
```

**Self-check 5:** `getppid()` must check `p->parent` because init has `parent == 0`. Reading `0->pid` would read
address 0 in the kernel (a kernel fault or garbage).
**Self-check 7:** `argint(0,&option)` means "copy the 1st integer argument of this system call, from the user stack,
into option". It returns −1 if the address is bad.
**Self-check 8:** `process_info(2)` needs the same check: init has no parent, so there is no parent PID to subtract.

**Viva extras**
- Only init (PID 1) has `parent == 0`, so options 1 and 2 return −1 only there.
- `p->parent` is read without `ptable.lock`. If the parent exits at that moment, `exit()` re-parents us to init
  (under the lock). That is harmless for this lab. A fully safe version would read it in proc.c under `ptable.lock`.

**Handout warm-up, getppid():** the same recipe with no argument. Add `SYS_getppid`, the prototype, `SYSCALL(getppid)`,
`sys_getppid()` (return −1 if `p->parent == 0`, else `p->parent->pid`), the table entry, `ppidtest.c`, and `_ppidtest` in UPROGS.
