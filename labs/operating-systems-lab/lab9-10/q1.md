# Q1 — Non-preemptive scheduling (FCFS and priority)

[Open the exam solution](q1.c)

Modify the xv6 (x86) scheduler so that it uses non-preemptive scheduling, meaning that once a process is
given the CPU, it keeps running until it exits, blocks on an event such as I/O or wait(), or voluntarily calls
yield(). Remove or comment out the timer-interrupt yield() in trap() in trap.c, so clock ticks no longer force
a context switch. Record each process's creation time (ctime = ticks) in allocproc(), and change scheduler()
to select processes by priority, using creation time to break ties. For pure FCFS, select by creation time
alone. Test the implementation with a user program that forks several long-running CPU-bound children, and
run xv6 with CPUS=1.


## Exam answer to write first

Keep xv6’s context switch code. Under `ptable.lock`, scan for one RUNNABLE winner, then switch to it. For FCFS compare `(ctime, pid)`. For priority compare `(priority, ctime, pid)`, with smaller values winning. The PID breaks ties when several processes were created in one tick. Disable just the timer-triggered `yield()` in `trap.c`. With one CPU, the parent sets priorities before its first `wait()`, which lets the children run.

## Answers

1. **What makes xv6 preemptive?** The timer interrupt. On every tick, `trap()` calls `yield()`, which makes the
   running process RUNNABLE and calls `sched()`. If you comment that `if` out, ticks still happen and `ticks`
   still counts, but nobody is forced off the CPU.
2. **When can the scheduler choose, with no preemption?** Only when the running process gives up the CPU
   itself, through `sleep()` (it blocks on I/O, `wait()` or a pipe), `exit()`, or a voluntary `yield()`. The
   policy in `scheduler()` only decides *who goes next*. It cannot take the CPU away from anyone.
3. **Why `CPUS=1`?** With 2 CPUs, two processes really run at once. Children then overlap, and the order no longer
   shows the policy.
4. **Why a tie-break?** `ctime = ticks`, and a tick is 10 ms. The parent forks all four children within the same
   tick, so their ctimes are equal. Comparing pids makes the order deterministic: the smaller pid was created first.
5. **Why must the parent set the priorities?** In your version each child called `setpriority()` on itself.
   But with no preemption, child 4 (default priority 3, earliest ctime) runs to completion before children 5–7
   have even run, so the order stays FCFS. The parent is never preempted, so it can fork all the children, set
   all their priorities, and only then call `wait()`. Its `wait()` gives the scheduler a CPU with all the
   priorities already in place.
6. **Risks of this policy.** One long job holds the CPU and makes everyone else wait (the **convoy effect**).
   With CPUS=1, the shell doesn't even respond until the job ends. With priorities, low-priority jobs can
   **starve** if higher ones keep arriving.
