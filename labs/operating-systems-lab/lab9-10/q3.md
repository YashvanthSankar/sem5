# Lab 9–10 Q3: Proportional-share lottery scheduling

[Open the exam solution](q3.c)

Modify the xv6 (x86) scheduler to implement lottery scheduling, ensuring CPU time is distributed
proportionally rather than equally. Add an integer tickets field to struct proc, assigning a default of 10
tickets to new processes in allocproc(), and ensure child processes inherit their parent's ticket count during
fork(). Implement a system call settickets(int tickets) that allows a process to update its own ticket count.
Change scheduler() in proc.c so that, on each scheduling pass, it calculates the total number of tickets held
by all RUNNABLE processes, generates a pseudo-random winning ticket (by adding a simple pseudo-random number
generator to the kernel), and iterates through the runnable queue to find and run the winning process. Write a
user program that forks two CPU-bound children with a significant ticket disparity (e.g., a 4:1 ratio), lets
them compute concurrently for a set duration, and prints their respective loop iterations to demonstrate that
the CPU time received is roughly proportional to their ticket allocations.


## Viva questions (reconstructed, not in the PDF)

1. Why does lottery scheduling never starve a process?
2. Why is the measured ratio only roughly 4:1?
3. Why must `total` and the winner scan happen while holding the same `ptable.lock`?
4. Why run with `CPUS=1`?

## Steps / run

1. Fresh copy: `rm -rf xv6-public && cp -R xv6-clean xv6-public`
2. Make every change in `q3.c`, file by file (proc.h, proc.c, sysproc.c, syscall.h, syscall.c, user.h, usys.S, Makefile), and create `lotterytest.c`.
3. `make qemu-nox CPUS=1`, then at the `$` prompt: `lotterytest` (it runs for 30 s: `DURATION 3000` ticks).

## Exam solution

1. Default to 10 tickets and inherit the parent’s value at fork. `settickets` changes the caller’s own tickets. The upper bound in the code keeps the sum within range.
2. While holding `ptable.lock`, sum tickets over RUNNABLE processes. If the total is positive, draw a number in 1..total. In a second scan, select the first process whose cumulative share reaches the draw.
3. Keep timer preemption. With 40 and 10 tickets competing, the expected split is about 80% and 20%. A finite run varies. Positive tickets give each runnable process a chance each draw, with no fixed bound on its wait.
4. The two CPU-bound children share a stopping tick. Each prints its completed rounds of 10,000 iterations. The 10-ticket child waits five ticks after the timed work to stagger the two output lines. Compare the 40-ticket count with the 10-ticket count. Use one CPU so the children compete for the same CPU.

One QEMU run with one CPU produced 768430 rounds at 40 tickets and 207306 at 10 tickets, about **3.71:1**.
