# Q2 — Preemptive priority-based scheduling

[Open the exam solution](q2.c)

Modify the xv6 (x86) scheduler so that it uses preemptive priority-based scheduling instead of the default
round-robin policy. Add a priority field to each process's struct proc, where a lower value means higher
priority, and give every new process a default priority of 10 in allocproc(). Change scheduler() in proc.c so
that, on each pass, it selects the RUNNABLE process with the highest priority, breaking ties by earliest
creation time. Keep the timer interrupt's call to yield() in trap.c, so a running process is preempted on
every clock tick and the CPU always goes to the highest-priority runnable process. Implement a system call
setpriority(int pid, int priority) that changes a process's priority while holding ptable.lock, and that
calls yield() afterwards so the change takes effect immediately. Write a user program that forks several
CPU-bound child processes with different priorities, and show that higher-priority children complete before
lower-priority ones, even when they are created or raised in priority later.


## Steps / run

1. Start from a clean tree, or undo Q1's trap.c change. Here the timer `yield()` must stay **on**.
2. Make the changes in `q2.c`, file by file: proc.h, proc.c (allocproc, scheduler, setpriority),
   sysproc.c, defs.h, syscall.h, syscall.c, user.h, usys.S, Makefile, plus the new schedtest.c.
3. Build and run on one CPU:
   ```
   make clean
   make qemu-nox CPUS=1
   $ schedtest
   ```

## Real xv6 output

Example output. PIDs vary.
```
$ schedtest

Preemptive priority test (parent = 10)
PID 4 assigned priority 15
PID 5 assigned priority 10
Child PID 6 completed
PID 6 assigned priority 5
Child PID 7 completed
PID 7 assigned priority 1
Child PID 5 completed
Child PID 4 completed

All child processes completed.
```

How to read it:
- All the children start at 10, the same as the parent. The parent was created earlier (earlier tick, then smaller PID), so it
  keeps winning and goes on setting priorities.
- PID 4 → 15 and PID 5 → 10 are still not better than the parent's 10, so the parent continues.
- PID 6 → 5 is better than 10. The `yield()` in `sys_setpriority` hands the CPU over, and child 6 runs to
  completion. That is why "Child PID 6 completed" prints **before** "PID 6 assigned priority 5": the parent only
  gets back to its `printf` afterwards.
- The same happens for PID 7 → 1.
- Then the parent `wait()`s and sleeps. 5 (priority 10) runs before 4 (priority 15).
- The children finish in order 6 (5), 7 (1), 5 (10), 4 (15). 6 finished before 7 only because it was raised
  first. A child raised later still finished before the children with worse priorities.

## Answers

1. **Why `yield()` after setpriority?** Without it, the newly raised process would only get the CPU at the next
   timer tick, up to 10 ms later. `yield()` makes the scheduler re-decide now.
2. **Why does "completed" print before "assigned"?** Because the yield happens *inside* the setpriority call. The
   higher-priority child runs all the way to `exit()` before the parent returns from the syscall to its `printf`.
3. **Why does preemption work?** The timer `yield()` in `trap()` puts the running process back to RUNNABLE on every
   tick. `scheduler()` then picks again, so the highest-priority RUNNABLE process always gets the CPU.
4. **How are ties broken?** Compare creation ticks first. If two processes were created on the same tick,
   use the smaller PID because xv6 assigns PIDs in increasing order.
5. **Starvation.** Strict priority starves low-priority processes while higher ones are RUNNABLE. Here the parent
   (priority 10) got no CPU while 6 and 7 ran. The fix is **aging**: raise a process's priority the longer it waits.
6. **Why must `setpriority()` live in proc.c?** `ptable` is defined in proc.c and xv6 does not expose it in a header. sysproc.c
   only reads the arguments and calls the helper.
7. **Why hold `ptable.lock`?** The scheduler reads `priority` and `state` under the same lock. Changing them under
   the lock means the scheduler never sees a half-finished update, and no slot is freed or reused mid-loop.
