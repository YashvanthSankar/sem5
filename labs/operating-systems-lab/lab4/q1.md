# Q1 — POSIX Shared Memory String Broadcaster (Modern API)

Objective: Master the fundamental lifecycle of POSIX shared memory (shm_open, ftruncate, mmap, munmap, shm_unlink) and examine its virtual filesystem backing under Linux (/dev/shm).

Task Specifications:

1. Develop two standalone programs: posix_sender.c and posix_receiver.c.
2. posix_sender.c must:
   - Create a shared memory object named '/lab_shm_basic' with mode 0666 using shm_open(..., O_CREAT | O_RDWR, 0666).
   - Set its storage capacity to exactly 256 bytes using ftruncate().
   - Map the region into the calling process address space using mmap() with PROT_READ | PROT_WRITE and MAP_SHARED.
   - Prompt the user via fgets() to input a line of text, copy it into the mapped buffer, and pause using getchar() prior to exiting.
3. posix_receiver.c must:
   - Open '/lab_shm_basic' in read-only mode (O_RDONLY).
   - Map the segment using PROT_READ.
   - Print the sender's text, display the virtual memory address returned by mmap(), unmap the region, and invoke shm_unlink().
4. Terminal Verification:
   - While posix_sender is paused, open a secondary terminal. Inspect the entry via 'ls -la /dev/shm' and inspect the content via 'cat /dev/shm/lab_shm_basic'.

## Compile & run

**q1_sender.c**

*Linux; old glibc needs -lrt, glibc >= 2.34 does not*

```text
  gcc -Wall -o sender q1_sender.c -lrt
  gcc -Wall -o receiver q1_receiver.c -lrt

Run:
  Terminal 1:  ./sender            type: hello operating sys!!!     (it then pauses)
  Terminal 2:  ls -la /dev/shm
               cat /dev/shm/lab_shm_basic
               ./receiver
  Terminal 1:  press Enter
```

## Answers

**q1_sender.c**

**Theory / viva:**
- /dev/shm is a tmpfs (RAM-backed file system). A POSIX shm object is a file there,
  which is why ls and cat work on it.
- Permissions show 664 or 644, not 666: the mode passed to shm_open is masked by the umask
  (umask 002 -> rw-rw-r--, umask 022 -> rw-r--r--).
- ftruncate is required: a new object has size 0, and touching an mmap beyond the end of
  the object gives SIGBUS.
- MAP_SHARED makes writes visible to other processes (MAP_PRIVATE would be copy-on-write).
- close(fd) after mmap is fine: the mapping keeps the object alive.
- munmap removes the mapping from THIS process; shm_unlink removes the NAME. Memory is freed
  once the name is gone and nobody has it mapped. If nobody unlinks, it stays until reboot.
- The two processes usually print different virtual addresses for the same physical memory.

**q1_receiver.c**

**Notes:**
- O_RDONLY open + PROT_READ map: asking for PROT_WRITE here would fail with EACCES.
- The receiver calls shm_unlink because it is the last user (spec says so).
