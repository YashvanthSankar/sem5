# Q1 — Implement getprocstates()

[Open the exam solution](q1.c)

Lab 8, xv6-public (x86). Copied word for word from the lab sheet (VPL). Solution code: `q1.c`.

Implement the xv6 system call "getprocstates()", which identifies the calling process using "myproc()", retrieves and
prints its PID, name, and current state, and is invoked through a user program named "procstate.c". The system call
must also access and safely traverse the global process table, using appropriate locking, to print all processes whose
state is not "UNUSED". The output should list each process's PID, name, and state, such as "RUNNING", "RUNNABLE", or
"SLEEPING". The analysis should explain why "myproc()" only identifies the current process, why the process table
requires locking during traversal, and how these process states differ. Submit all modified kernel and user files,
identify the changes made, demonstrate the system call in xv6, and explain how process information and states are
retrieved without modifying the scheduler or adding new states.

## Expected demonstration

Run `procstate`. Its own row shows RUNNING. On an otherwise idle system, init and the shell typically show SLEEPING while waiting for children. To see more states, run it while another process spins or while an exited child awaits `wait()`.

## Viva

- `myproc()` yields the current CPU's running process. Walking `ptable.proc` gives you the rest.
- Copy each occupied row under `ptable.lock`, then release it before calling `cprintf`. Console interrupts may already hold the console lock when they call `wakeup()`, which takes `ptable.lock`. Printing under the table lock would reverse that lock order.
- RUNNING uses a CPU, RUNNABLE is eligible to run, and SLEEPING waits for a wake-up. ZOMBIE awaits reaping. No scheduler changes are needed.
