Add a new system call int getprocs(struct uproc *buf, int max) to xv6 (x86) that reports every process

## Exam answer to write first

Define the shared `struct uproc` and wire up the system call. In `sys_getprocs`, read `max` with `argint`, check its size, then validate the buffer with `argptr`. In `proc.c`, hold `ptable.lock` and copy up to `max` occupied entries. Return the number copied. In `ps.c`, loop over just those entries and print them. For the extension, zero `nrun` in `allocproc`, increment it when the scheduler chooses the process, and export it with the other fields.

## Answers

- **A1. Why ps is always RUNNING:** `getprocs()` runs inside ps's own system call. With one CPU, the process making a
  syscall is the one the scheduler set to RUNNING (`c->proc`). Every other process is off the CPU at that moment.
- **A2. Why init and sh are SLEEPING, and where:** `init` (PID 1) loops in `wait()`; with no zombie child it calls
  `sleep(curproc, &ptable.lock)`. `sh` (PID 2) forked ps and is in `wait()` for it (`if(fork1() == 0) runcmd(...); wait();`
  in sh.c). When sh is idle at the prompt it sleeps in `read()` on the console (`consoleread` → `sleep(&input.r, ...)`).
- **A3. Why init's PPID is 0:** init is not made by `fork()`. `userinit()` builds it directly, so `p->parent` is null and
  `getprocs()` reports 0.
- **A4. When ZOMBIE appears:** between a process's `exit()` and its parent's `wait()`. In ztest the child (PID 9) exits at
  once while the parent (PID 8) is in `sleep(300)`, so ps shows `9  8  ZOMBIE  ztest`. When the parent calls `wait()`, the
  slot becomes UNUSED and the zombie disappears.
- **A5. RUNNABLE and timer preemption:** yes, `12  1  RUNNABLE  spin`. spin never blocks, yet ps got the CPU. So the
  **timer interrupt preempted spin** (`yield()` in `trap()` set it RUNNABLE) and the scheduler chose ps. Without timer
  preemption ps could not run until spin exited. With one CPU only one process is RUNNING; the other CPU-hungry one is RUNNABLE.
- **Viva: why background jobs have PPID 1, and why init prints `zombie!`:** for `cmd &`, sh forks a child that forks the
  command and exits at once (`BACK` case in sh.c). The command's real parent is gone, so it is re-parented to init (PPID 1).
  When it finishes, init's `wait()` reaps it; it is not the shell init started, so init.c prints `zombie!`
  (seen twice above: for sleepy and for ztest).

### E2. nrun comparison (real numbers above)

| Process | What it does | nrun |
|---|---|---|
| spin (CPU-bound) | never blocks | 307 → 593 in 3 s, about 95 per second |
| sleepy (`sleep(500)`) | "sleeps" 5 s | 109 after ~1 s, 408 after ~4 s, about 100 per second |
| init, sh | block in `wait()` / `read()` | 24–50, barely move |

- **spin** is preempted every tick and picked again, so `nrun` rises about once per tick (100 ticks per second).
- **sleepy rises just as fast.** `sys_sleep` sleeps on `&ticks`, and every timer tick `wakeup(&ticks)` makes it RUNNABLE.
  It runs for a moment, sees fewer than 500 ticks have passed, and sleeps again. So a process in `sleep()` can still be scheduled on most ticks.
- **init and sh** wait on channels that are only woken by a wake-up on their respective wait channels (a child exiting, console input), so they are almost
  never chosen.
- **Conclusion:** `nrun` counts how often a process is *chosen*, not how much CPU it used. spin uses a full tick each time;
  sleepy is chosen as often but runs for microseconds each time.
